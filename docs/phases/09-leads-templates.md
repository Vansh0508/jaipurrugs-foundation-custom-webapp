# Phase 9 — Leads, Custom Attributes & WhatsApp Template Management

Builds on [phase 8](08-ai-agent.md). Adds a lead list system with custom attributes, syncs form submissions into leads, lets the WhatsApp agent collect contact details, and manages WhatsApp templates in-app. Every template variable is filled from lead data when the agent sends it.

## Scope

- Schema (`supabase/migrations/20261002160000_leads_and_template_bindings.sql`):
  - `lead_attributes`: global custom fields. `key` is immutable; `type` is `text | number | date | select`; `description` tells the agent what to ask; `is_active` deactivates an attribute without deleting its data.
  - `leads`: one row per phone (unique on `phone_normalized`, generated by `normalize_phone()`). `attributes` is JSONB keyed by attribute key. `source` is `form | whatsapp_agent | manual`.
  - `lead_lists` + `lead_list_members`: named lists. A lead can be in many lists.
  - `form_lead_mappings`: per form, which field is the phone, which is the name, field → attribute map, and the lists to add submitters to.
  - `whatsapp_template_bindings`: per template name + language, which lead field fills each variable, plus an optional fallback.
  - Functions: `answer_to_text`, `lead_attribute_value` (type coercion), `agent_upsert_lead` (invoker), `private.sync_lead_from_submission` (definer), `sync_form_leads` (definer, active-member check).
  - Trigger `trg_form_submissions_sync_lead` runs on `form_submissions` when a submission becomes `completed`.
- Zernio (`src/lib/zernio/client.ts`): `createWhatsAppTemplate`, `deleteWhatsAppTemplate`. Listing and sending already existed.
- Shared logic: `src/lib/leads/fields.ts` (field refs `name | phone | attr:<key>`), `src/lib/whatsapp/templates.ts` (summaries, variable keys, preview), `template-builder.ts` (draft model, Meta authoring rules, Zernio payload), `bindings.ts` (server-side variable filling).
- Agent: `getLeadProfile` and `saveLeadDetails` (`src/lib/mastra/tools/leads-tool.ts`). `sendWhatsAppTemplate` now takes only `templateName` + `language`.
- UI: `/leads` (leads, lists, custom attributes), `/forms/[id]/leads` ("Lead sync" tab), `/templates` (list, preview and variable setup, delete), `/templates/new` (builder with live preview).

## How template variables are filled

1. Each variable has a stable key: `header:1`, `body:artisan_name`, or `button.<i>:1`. Two URL buttons can both use `{{1}}` without colliding.
2. A binding maps each key to a lead field, plus an optional fallback.
3. At send time, `resolveTemplateParams` reads the session contact's lead (by phone) and fills every slot. **The model never supplies values.** Anything it passes beyond `templateName`/`language` is stripped by zod.
4. A missing value with no fallback blocks the send and returns `missing` with each attribute's `description`. The agent asks the contact, saves the answer with `saveLeadDetails`, then sends again.
5. Deactivated attributes are never sent, even if a value is stored. A binding that points at one shows as "Uses a deactivated attribute" in Templates.

## Form → lead sync

- **Live:** completing a submission fires the trigger. Answers are coerced to each attribute's type; values that don't fit are skipped. The new value wins per field, and nothing known is erased. Errors are caught and logged as warnings, so lead sync can never block a public form submission.
- **Backfill** ("Sync existing submissions"): newest submission first, **gap-filling only**. Replaying old submissions never overwrites newer data, such as details the agent collected.
- The sync is `SECURITY DEFINER` in the `private` schema, which isn't exposed through the Data API. Anonymous form fillers trigger it but can't read or write leads.

## Do's

- Give new agent tools that touch leads `AgentToolContext` + `LeadLoader`, with no phone/identity arguments. Call `leads.invalidate()` after a write.
- Deactivate attributes instead of deleting them, so stored values and history survive.
- Keep the template authoring rules in `validateDraft` aligned with Meta's. The server re-validates every draft before calling Zernio.

## Don'ts

- Don't let the model pass template parameter values. Add a lead attribute and bind the variable to it instead.
- Don't change an attribute's `key` or `type` after creation. Form mappings, bindings and stored values depend on them.
- Don't add media headers until Meta's media-handle upload flow through Zernio has been verified. Builder headers are text-only.

## Not in this phase

- Manual lead creation and CSV import. Leads come from forms and the agent; existing leads can be edited.
- Template editing. Meta allows limited edits, and each one sends the template back to review. For now, delete and recreate.
- Sending templates to a whole list (Zernio broadcasts). The bindings and `resolveTemplateParams` are built so this can reuse them.
